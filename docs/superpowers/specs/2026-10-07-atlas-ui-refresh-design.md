# ATLAS 목업의 실제 고객 서비스 UI 적용 명세

기준일: 2026-10-07

상태: 사용자가 2026-10-07 다크 포함 최종 계획과 페이지·기능 담당 실행을 승인했다. Tasks1–10의 공통 기반·네 메뉴 구현/독립 검토를 완료했고 Task11 통합 QA를 진행 중이다. 전체 검증·로컬 병합은 아직 완료하지 않았다.

## 1. 목적과 승인 기준

승인된 ATLAS compact 목업과 브라우저 수정 의견을 실제 React 고객 서비스에 적용한다. 공통 컴포넌트와 디자인 역할을 먼저 통일하고, 모니터링·제어·통계·설정 담당 에이전트가 이를 소비한다. 기존 API, 권한, 명령 실행·복구, 실제 도면과 데이터의 의미는 유지한다.

- 최신 추가 요구: 모바일 헤더에도 실제 킨다 로고를 표시하고 현장 선택의 너비를 줄인다.
- 추가 확정: 이번 실제 구현에 라이트·다크 전환과 선호 테마 저장을 함께 포함한다.
- 공통 도면 상태는 큰 카드 네 칸이 아니라 기존 인라인 배치에서 글자만 조금 키운다. 모니터링과 수동 제어에 동일하게 적용한다.
- 수동 제어의 이동·개별 선택·영역 선택 도구는 도면 패널 상단에 붙인다.
- PC 수동 제어는 화면 바깥 세로 스크롤 없이 도면·밝기 적용·이력에 접근한다. 모바일은 자연스러운 세로 스크롤을 유지한다.
- 실제 구현은 별도 브랜치에서 진행하고 검증 후 기존 개발 브랜치에 로컬 병합한다. 원격 push, PR, 배포, DB 변경, 실장비 조작은 포함하지 않는다.

디자인 기준은 [보존된 목업](../../assets/atlas-ui-refresh-2026-10-07/README.md)이다. 마지막 모바일 로고 의견은 이 명세의 추가 기준이며 보존된 목업에는 아직 반영되지 않았다. 목업은 디자인 참고 자료이며 제품 구현·데이터·안전정책의 정본이 아니다.

## 2. 적용 범위와 선택한 접근

### 선택: 기존 제품 구조 위에 공통 표현 계층 적용

React Aria 기반 입력·버튼·오버레이, Tailwind semantic token, 기존 기능 모듈을 유지한다. 공통 UI를 먼저 확장한 뒤 네 메뉴와 그 하위 화면을 같은 표현 계약으로 전환한다. 페이지별 별도 버튼·카드·필터·테이블을 만들지 않는다.

다른 접근의 비용은 다음과 같다.

1. 목업 HTML/CSS/전역 상태를 직접 이식하면 React Aria 접근성, 실제 API 수명, 명령 복구와 정책 검사를 다시 구현해야 한다.
2. 페이지별 스타일만 바꾸면 중복과 디자인 차이가 남고 공유 지도·필터 소비자 사이의 회귀를 발견하기 어렵다.

이 작업은 공통 구조와 소비자 인터페이스를 함께 바꾸는 아키텍처 변경으로 취급한다. 승인된 목업 방향은 명세 작성의 근거이고, 서면 명세와 이후 실행 계획의 검토를 제품 구현 승인으로 대체하지 않는다.

### 범위 밖

- API·공유 스키마·DB·MQTT·Gateway·펌웨어 계약 변경
- 공개 랜딩, 로그인, 운영자 UI의 신규 디자인
- 목업의 가상 데이터, 성공/실패 시나리오 선택, 가상 Gateway, 가짜 SVG 도면, 예시 초기화 기능의 제품 이식
- 새 센서 이벤트, 새 통계 집계 API, 가짜 보고서 완료·다운로드
- 기존 기능을 감추거나 삭제해서 화면 높이를 맞추는 변경

### 테마 범위와 수명

이번에는 **라이트·다크의 실제 전환과 저장까지 구현**한다. 기본값은 라이트이며 시스템 테마 자동 연동은 추가하지 않는다. 고객 헤더의 44px 아이콘 버튼으로 전환하고 현재 다크 여부를 `aria-pressed`로, 실행할 동작을 `라이트 모드로 변경` / `다크 모드로 변경`으로 알린다.

- 저장 키는 `led-control.customer-theme.v1`, 값은 `light` 또는 `dark`다. 계정·현장·명령 저장소와 분리된 브라우저별 UI 선호값이다.
- 최초 진입·새로고침에서 저장값을 읽는다. 값 없음·잘못된 값·읽기 실패는 라이트다. 저장 실패해도 현재 탭의 전환은 유지하며 동작을 막지 않는다. 같은 origin의 다른 탭에서 발생한 storage 변경을 반영하고 키 삭제는 라이트로 복귀한다.
- CustomerShell의 안정된 provider가 고객 화면이 활성화된 동안만 html의 `data-customer-theme="light|dark"`를 소유한다. root에 선언된 semantic 역할 alias를 통해 body portal의 오버레이와 computed color reader까지 같은 테마를 사용한다. 고객 화면을 떠나면 자신의 속성만 정리해 비고객 기본 팔레트를 복원한다.
- 초기 적용과 CSS alias 변경 뒤 palette 발행은 layout 경계에서 수행하여 첫 고객 프레임에 다른 테마가 깜빡이지 않도록 한다. StrictMode setup/cleanup, 로그아웃·역할 전환, 빠른 재진입과 storage listener cleanup을 검증한다.
- React context가 읽은 palette를 발행하여 차트·canvas의 색상만 다시 그린다. theme를 App/Route/QueryClient/command/editor scope·key에 넣거나 고객 subtree를 재마운트하지 않는다.
- 원본 CAD/저장 도형의 지정 색상과 사용자가 수정한 색상 draft는 보존한다. 테마는 배경·글자·선택·가이드·상태 chrome에만 영향을 준다. 테마 전환으로 명령·저장·다운로드·MFA 요청을 추가 발행하지 않는다.
- native OS status bar·앱 바깥 frame의 테마 전환은 범위 밖이다. WebView 내부 고객 화면과 기존 safe-area 소유 계약은 유지한다.

## 3. 디자인 시스템과 공통 UI 계약

### 토큰과 적용 경계

`apps/web/src/styles/theme.css`의 단일 `@theme static`을 계속 정본으로 사용한다. 고객 라이트/다크 palette는 `--color-customer-{light|dark}-{role}`로 평평하게 선언하고, `styles/base.css`의 정확한 두 고객 root selector에서 기존 semantic 역할을 그 palette에 연결한다. CSS alias에는 literal 색상을 넣지 않는다. 기본 공통 표현과 brand·landing 역할은 보존하여 로그인·운영자·공개 화면을 의도치 않게 바꾸지 않는다.

| 고객 역할 | 라이트 | 다크 |
| --- | --- | --- |
| 화면 / 패널 / inset | `#F4F7FB` / `#FFFFFF` / `#EEF2F8` | `#0F1724` / `#182334` / `#1E2D44` |
| 본문 / 보조 | `#152C43` / `#526477` | `#EAF1FA` / `#B0BDCE` |
| 기본 경계 / 입력 경계 | `#D8E1EC` / `#7B8B9C` | `#33465D` / `#647C98` |
| 주요 동작 / 동작 글자 / 선택 배경 | `#245FE8` / `#FFFFFF` / `#E9F0FF` | `#94B9FF` / `#0F1724` / `#263D68` |
| 정상 / 주의 / 오류 | `#187445` / `#946000` / `#B4233C` | `#70D6A4` / `#F2C46D` / `#FF91A5` |
| 지도 배경 / UI 선 / UI room | `#EDF2F7` / `#64758A` / `#F7F9FC` | `#111C2B` / `#7F95B1` / `#1C2C43` |

hover/focus/disabled, 상태 badge·feedback, chart/heatmap와 fixture editor UI 역할도 토큰 전수 매핑의 대상이다. `content-inverse`를 다크 primary 글자 역할로 바꾸지 않고 `action-primary-foreground`를 독립 역할로 추가한다. 원본 CAD·도형 색상은 테마 팔레트에서 제외한다. 두 root selector는 정확한 선언 집합·개수로 검토하며 일반 selector/style 예외를 허용하지 않는다.

Task11 실제 포커스 검사에서 기존 고정 반투명 `shadow-focus`의 고객dark 대비1.3116:1 미달을 발견했다. 기존 기본shadow와579선언을 보존하고, 이미 승인된 고객 `border-focus` light/dark 색을 쓰는3px 불투명 고객shadow2를 추가한다. 공통컨트롤의 기존 `shadow-focus` 소비는 바꾸지 않고 정확두customer root에서만 shadowalias를 연결한다. 토큰 전용/독립검토 뒤 실제hash anchor 회전과 closed정책을 적용하며 기본·brand/landing/login/operator는 그대로다. 현재는 수리 관문이며 새shadow GREEN·전체focus/모든surface/physicalnative 완료를 뜻하지 않는다.

간격은 기존 승인 스케일을 재사용한다. 반복 section·panel 간격, typography, control 반경과 focus ring은 공통 컴포넌트가 소유한다. 목업의 숫자와 색상을 소비자에 literal로 복사하지 않는다. 새로운 layout 치수와 typography 역할은 소비 목적을 문서화해 승인 토큰으로 추가한다.

기존 정책은 승인 앵커 `7b2617b173618d376e7b3a90ec31e1392c3b7bc0`의 375개 역할을 고정한다. 변경 순서는 역할 매핑 검토 → 토큰 전용 커밋 → 별도 정책 앵커 회전 검토·문서 갱신 → 전체 정책 검사 → 공통 컴포넌트 → 메뉴 소비자다. 중간 토큰 커밋의 예상 정책 실패를 전체 통과로 표시하지 않는다. 빈 baseline, Git object 누락 시 차단, 금지 literal·selector·native form 규칙은 유지한다.

| 도면 chrome | 제목/인라인 집계/선택 도구/카메라 footer의 표현을 공유한다. 데이터·선택·제어 명령은 소유하지 않는다. |

기존 모바일 utility 경계인 `max-compact`의 **760px 미만**을 따른다. 목업의 680/700px 분기나 legacy CSS의 760px 포함 조건을 섞지 않는다. 759.5/760/760.5px 경계를 검증한다. 모든 조작은 최소 44px hit 영역을 유지하며 지도에 이미 더 큰 hit 영역이 있으면 줄이지 않는다.

sidebar의 영문 부제와 중복 현장 안내는 정리하되 헤더의 실제 현장 선택·집계와 권한·운영 경고는 보존한다. 접힌 rail에는 메뉴 이름을 알 수 있는 접근성 이름과 tooltip을 제공한다. 목업의 가상 Gateway 현장 카드는 제품에 추가하지 않는다.

### 지도 도구와 높이

공유 지도 구현자는 FloorMapViewport와 SpatialTargetSelector의 소비자를 먼저 조사한다. 수동 제어에서는 사용자가 선택한 pan/select/area 모드가 실제 gesture 정책에 반영되도록 명시적 계약을 둔다. 다른 등록·스케줄·이벤트·구역 편집 소비자의 기존 interactionPolicy를 무조건 바꾸지 않는다.

PC 수동 제어는 shell 아래 남는 높이를 flex/grid로 배분한다. 외부 문서 세로 스크롤은 없고 도면/우측 제어/하단 한 줄 이력이 배치된다. 결과·경고·복구 내용은 제어 패널의 내부 스크롤 영역에 놓고 실행 버튼과 복구 동작을 끝까지 접근할 수 있게 한다.

- 표준 PC 검증: 1304×1229, 1440×900, 1024×768 및 760px 경계의 768px 높이.
- 짧은 PC 1024×600: 실제 지도 canvas 최소 240px과 모든 안전 안내를 보존한다. 높이가 부족하면 **내부 workspace 스크롤**로 전환하여 전체 기능에 접근한다. 외부 문서 스크롤 차단만으로 내용을 잘라내지 않는다.
- 모바일: 자연 세로 스크롤, 항상 노출된 지도 도구와 밝기 설정·적용 버튼. 도구/실행 설정을 펼쳐야만 접근하는 별도 disclosure는 제거한다.
- 크기 변경·지도 전체 보기·복귀 시 camera 상태, 좌표 변환, 선택, focus, resize cleanup을 보존한다.

## 4. 메뉴별 적용

### 모니터링

- 불필요한 설명·도면 사용 안내를 제거하고 제목, 실제 마지막 갱신 시각, 새로고침, 층 선택·검색/상세·목록을 명확히 배치한다.

### 제어

- 수동 제어·스케줄·이벤트·그룹/구역의 공통 탭 표현을 적용한다. 기존 `mode=manual|schedule|event` 링크와 siteId/query/hash는 보존하고 `mode=group`을 frontend mode로 추가한다. manual/group 조회는 현재 제어 페이지 진입 capability를 따르고 schedule/event는 manage가 필요하다. group 변경은 canManage를 따르며 일반 제어 사용자의 기존 구역 현황 조회를 제거하지 않는다.
