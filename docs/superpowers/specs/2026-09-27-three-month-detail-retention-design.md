# 최근 3개월 상세 기록 보존 — 단순화 설계

작성일: 2026-09-27

## 목적과 결정

사용자가 읽는 모니터링 로그와 제어 명령의 상세 내용은 중앙 DB 기준 최근 **3 calendar months**만 보존한다. 조명을 잘못 재실행하지 않기 위한 작은 내부 식별자·처리 상태는 상세 기록과 구분해 더 오래 보존할 수 있다. 1년 유료 보관, 요금제 UI, 과거 삭제 데이터 복원은 이번 범위가 아니다.

이 설계는 기존 `Command` **행 전체를 물리 삭제**하려던 계획을 대체한다. 기존 행과 필수 FK는 유지하고, 안전하게 끝난 행의 내용과 파생 사본만 비운다. 기존 물리 purge 및 그 전용 보호 cutover는 활성화하지 않는다. 운영 중앙 DB·Gateway·브로커는 설계 승인만으로 변경하지 않는다.

성공 기준은 (1) 일반 화면과 인증된 API가 3개월 이전 상세를 반환하지 않는 것, (2) 완료된 오래된 명령의 중앙 DB 상세 내용과 안전하지 않은 복사본이 실제로 제거되는 것, (3) 같은 요청 ID의 재전송과 늦은 ACK가 새 밝기 제어를 만들거나 지운 상세를 복원하지 않는 것, (4) 미확정 명령·활성 override의 제어 잠금이 유지되는 것이다.

## 선택한 방식과 대안

**선택: 기존 행의 내용 제거.** `Command`와 필요한 전송 식별자는 남기되, 삭제 시각(`contentRedactedAt`)과 DB 무결성 조건을 추가한다. 별도 3개월 상세 이력 테이블을 만들고 기존 원본을 계속 보관하는 방식은 중앙 DB 상세 삭제 요구를 충족하지 않는다. 원본 행 전체 삭제는 현재 FK·outbox·override·늦은 응답을 한꺼번에 이관해야 하므로 사용자가 원한 단순화와 맞지 않는다.

## 데이터 경계

| 종류 | 3개월 뒤 처리 |
| --- | --- |
| `MonitoringActivity` 고객 로그 | 기존 DB UTC 기준 조회·bounded 물리 정리 유지. 오래된 cursor는 기존 계약대로 만료 처리. |
| 종료된 `Command`의 사람이 읽는 내용 | 대상 종류·ID·조명 목록, 밝기, 오류 문구, 원문에서 추측 가능한 fingerprint 등을 제거한다. 일반 이력에서 제외하고 상세는 권한 확인 뒤 내용 없는 `410 command_expired`를 반환한다. |
| 완료된 명령의 파생 상세 | 조명별 결과, 전송/ACK의 raw payload, 종료된 수동 override·manual `AutomationExecution`의 상세 사본을 같은 삭제 정책으로 감사하고 안전한 순서로 제거한다. 모든 사본이 정리되지 않은 후보는 완료로 표시하지 않는다. |
| 내부 안전 상태 | 현장·명령의 opaque ID, 생성 시각, 종료 여부, 기존 UUID 요청 키와 필요한 dispatch sequence/상태만 남긴다. 사용자명·대상·밝기·원문 오류는 남기지 않는다. 요청 키는 중복 방지 외 조회에 노출하지 않는다. |
| 미해결 명령·활성 override | **안전 예외:** 실제 조명과 기대 밝기가 상태 확인에 필요한 동안 별도 제한된 운영 상태로 유지한다. 일반 3개월 이력에는 노출하지 않는다. 해결되면 다음 정리 주기에 상세를 제거한다. 이 예외의 보유량·나이와 해결 필요 건수를 운영자에게 알린다. |

`Command`의 비어 있는 내용은 정상 명령으로 해석할 수 없도록 명시적 상태와 DB 검증을 둔다. 기존 비어 있지 않은 행을 조회하는 모든 Set/Get/이력 경로는 이 상태를 검사한다. 새 명령 생산자의 내용 필드는 이전과 동일하며, 기존 마이그레이션이나 과거 시각을 소급 재작성하지 않는다.

## 정리와 조회 흐름

1. 중앙 DB UTC transaction 시각에서 `3 months`를 뺀 경계를 사용한다. 정확한 경계에 있는 기록은 남기고 그 이전만 후보로 삼는다. 미래 1년 요금제는 별도 설계에서 이 기간을 선택하게 하며, 이미 삭제된 상세를 되살릴 수 없다.
2. 작은 배치에서 후보를 잠그고 완료 상태, 미해결 hold 없음, 활성 override 없음, 발행 대기·lease·ACK 의무 없음, raw 사본 정리 가능성을 확인한다. 하나라도 불확실하면 그 명령은 건너뛰고 이유와 지연 건수를 기록한다. 이 단계는 장비에 Set/Get을 발행하지 않는다.
3. 확인된 후보만 한 transaction에서 원본 내용과 안전하게 종료된 파생 상세를 제거하고 `contentRedactedAt`을 기록한다. 실패 시 전부 rollback한다. 같은 작업을 다시 실행해도 추가 명령이 생기거나 상세가 돌아오지 않는다.
4. `GET /commands`는 독립적으로 최근 3개월만 반환한다. 이 읽기 제한은 원본 물리 삭제나 새 복구 POST를 켜야만 작동하도록 묶지 않는다. 오래된 상세의 알려진·인가된 ID는 410, 존재하지 않거나 다른 현장의 ID는 구별 불가능한 404를 유지한다. 기존 cursor 오류 코드는 유지한다.
5. 중복 `clientRequestId`가 내용 제거된 행에 걸리면 기존 결과를 재실행·재구성하지 않고 충돌로 거부한다. 늦은 ACK도 저장된 안전 식별자로 소비하되 원래 내용이나 새 조명 결과를 다시 만들지 않는다. 이 동작은 일회용 DB와 HTTP 통합 테스트로 먼저 입증한다.

## 화면·API 경계

제어의 일반 명령 이력과 모니터링 로그 드로어는 최근 3개월 상세만 표시한다. 미해결 안전 건은 일반 이력의 빈 행이 아니라 별도의 ‘확인 필요’ 상태로 표시한다. 이미 열린 상세가 만료·권한 상실·재조회 오류를 만나면 cached payload와 재실행 동작을 숨긴다. 404만 보고 제어 잠금을 풀지 않으며, 잠금 해제는 새로 인가한 정확한 case 조회 결과에 따른다.

현재 Web이 호출하는 case 상태 확인·위험 해제 POST는 API에 등록되지 않아 실제 요청이 404다. 이 설계의 기록 정리를 켜기 전에 버튼을 실제 안전한 API와 연결하거나, 서버 기능이 준비될 때까지 비활성 사유를 명확히 표시한다. 본 설계는 그 POST나 새로운 자동 Get 복구를 필수 전제로 삼지 않는다. 기존 3개월 안의 수동 제어·기존 상태 확인 기능은 유지한다.

## 검증·출시 경계

- 먼저 RED→GREEN 테스트로 월말·윤년·정확 cutoff, DB session UTC/Seoul/New York, API clock 차이, 1,001개 이상 배치, 동시 처리/rollback을 확인한다.
- 미해결/활성/발행 대기 후보는 원문을 유지하고 일반 이력에서는 숨긴다. 완료 후보의 Command·결과·outbox·manual copy·활동 source에 상세 복사본이 남지 않는지 일회용 PostgreSQL에서 검사한다.
- 중복 요청·late ACK·401/403/404/410·기존 status-check·제어 잠금·Web stale cache를 회귀 검증한다. 안전 상태가 부족하면 flag를 켜지 않고 후보를 건너뛴다.
- 운영 DB에서는 백업, schema/권한 검사, 기존 비UTC 행 감사, dry-run 후보·예외 수, 짧은 배치 관측을 거친다. 물리 `Command` 행 purge flag와 미설치 보호 cutover는 계속 OFF다. 실제 Gateway RF/HIL은 제품 제어 검증으로 별도 보고하며, 이 상세 정리 작업이 새 Set/Get을 발행하지 않는다는 소프트웨어 증거와 혼동하지 않는다.

## 문서와 작업 경계

스키마 변경 때 `docs/database-schema.md`, 제어·모니터링 동작 변경 때 각 `docs/menus` 문서를 같은 작업에 갱신한다. 이전 2026-09-25 원본 행 삭제 계획은 기록으로 보존하되 이 결정 이후 구현 목표로 사용하지 않는다. 현재 공유 worktree의 다른 미커밋 파일과 실험 cutover는 사용자 소유 상태로 보존하고, 이 설계의 선택 파일만 별도 검증·리뷰한다.
