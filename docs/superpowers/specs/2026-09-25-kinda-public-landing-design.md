# 킨다 공개 랜딩 및 상담 문의 설계

기준일: 2026-09-25

## 목적과 범위

킨다를 구매하거나 도입할 기업 고객이 서비스를 이해하고 상담을 신청할 수 있는 공개 랜딩 페이지를 만든다. 첫 번째 고객군은 주차장·시설 운영 담당자, 두 번째 고객군은 조명 시공·유통 파트너이며 두 고객군의 가치를 비슷한 비중으로 설명한다. 기존 `led-control-service/apps/web`에 배치하고, 상담 문의는 같은 서비스의 API가 접수해 `kymkjh2002@dfkorealed.com`으로 보낸다.

기존 인증·관제 화면과 API 계약은 유지한다. 실제 장비에서 측정되지 않은 절감률, 가용률, 통신 성공률을 주장하지 않는다. 제품 화면 예시는 실제 운영 데이터로 오인되지 않게 명시한다.

## 참고와 시각 방향

- Figma 한국어 홈페이지의 큰 제목, 명확한 탐색 및 CTA, 제품 화면을 중심으로 이어지는 섹션 구성을 참고한다. 문구·로고·이미지·레이아웃을 복제하지 않는다.
- 사용자 선택은 **대시보드 화면을 앞세운 차분한 구성**이다. 킨다 브랜드의 Navy `#15324A`, Blue `#256FA1`, Coral `#FF7A5C`, Paper `#F4F8FA`를 기존 역할대로 사용한다. Coral은 장식에만 사용하고 본문·주요 버튼에는 쓰지 않는다.
- 첫 화면은 킨다 로고, 간결한 내비게이션, `조명 운영을 간단하게.`와 한 문장의 제품 설명, 상담 CTA와 로그인 링크, 넓은 관제 대시보드 예시로 구성한다. 대시보드 예시는 현장/층/지도·상태·제어·통계의 시각적 관계를 보여주는 벡터/HTML 자산이며 `제품 화면 예시`라고 표시한다. 임의의 성과 수치나 고객 로고는 넣지 않는다.
- 아래에는 운영 담당자의 `현장 상태 확인 → 필요한 대상 제어 → 운영 기록 검토`, 파트너의 `설치 정보 정리 → 인수인계 → 유지관리` 흐름을 각각 설명한다. 각 기능은 현재 소프트웨어 기능 범위와 일치하는 표현만 사용한다.
- 반응형 320px 이상, 키보드 탐색, 의미 있는 제목 계층, 대비, 축소 동작 설정을 지원한다. 장식 애니메이션은 필수가 아니다.

## 공개 경로와 인증 경계

- `/`는 공개 랜딩 페이지다. 페이지 표시를 위해 `/auth/me`를 호출하거나 로그인 상태를 요구하지 않는다.
- `로그인`은 기존 인증 화면으로 이동한다. 권장 경로는 `/login`이며, 기존 인증 셸이 로그인 완료 후 고객은 `/monitoring`, 운영자는 `/operator/site-admins`로 안내하는 동작을 유지한다.
- 기존 고객·운영자 경로의 권한 확인, 오류 복구, 세션 교체 동작을 변경하지 않는다. 공개 페이지에서 내부 관제 데이터를 가져오지 않는다.
- 공개 페이지 내 내비게이션은 기능, 대상별 가치, 상담 양식으로 이동한다. 모바일에서도 접기 메뉴 또는 단순 링크로 모두 접근 가능하다.

## 상담 양식과 상태

- 필수: 회사명, 담당자 이름, 회신 이메일, 문의 내용, 개인정보 수집·이용 동의. 선택: 전화번호, 고객 유형(운영/시공·유통). 파일 첨부와 계정 생성은 없다.
- 안내에는 수집 목적(상담 접수·회신), 항목, **접수 후 90일** 보관, 동의 거부 시 온라인 접수 제한, 메일 사본은 NAVER WORKS의 보유 정책을 따른다는 점을 명시한다. 동의 문구는 버전과 동의 시각으로 기록한다.
- 제출 중 중복 클릭을 막고, 접수 완료 시 접수번호를 보여준다. 접수 완료는 서버 DB 저장을 뜻하며 메일의 최종 수신을 보증하지 않는다. 네트워크 오류에서는 입력을 보존하고 재시도를 제공한다. 응답 유실 후 같은 요청을 다시 보낼 때 동일 접수번호를 돌려준다.
- 서버는 형식·길이·동의 버전을 검증하고 고정된 수신 주소만 사용한다. IP별 요청량 제한, 작은 본문 크기 제한, honeypot 필드, HTML 이스케이프를 적용한다. 입력값·이메일 주소·토큰을 오류 로그에 남기지 않는다.

## 서버 접수, 메일 발송, 보관

- `POST /landing/inquiries`는 인증 없는 공개 API다. 멱등 키와 정규화된 payload hash를 저장하고 같은 키/같은 내용은 기존 접수를 반환한다. 같은 키/다른 내용은 충돌로 거부한다.
- 새 Prisma 모델은 문의 원본, 동의 버전·시각, 90일 만료일, 발송 상태와 재시도 메타데이터를 저장한다. DB 트랜잭션으로 원본과 발송 대기 상태를 함께 확정한다. 90일이 지난 원본·발송 기록을 주기적으로 삭제하고 실제 삭제 결과를 관측한다.
- 메일 발송은 `회사 홈페이지`의 NAVER WORKS OAuth/HTTPS 전송 패턴을 참고해 **관제 서비스 내부에 독립 구현**한다. 메일 API는 구성원 OAuth `mail` 범위가 필요하며, 액세스·리프레시 토큰은 암호화해 저장한다. 운영자만 연결 상태를 확인하고 OAuth 연결을 시작할 수 있다. 비밀값은 서버 환경 변수/secret store에서만 읽는다.
- 발신자와 수신자는 서버 설정으로 고정한다. 전송 요청에 신청자가 입력한 주소를 `from`으로 쓰지 않고, 회신 정보는 본문에 포함한다. NAVER WORKS가 `202 Accepted`를 반환한 경우만 `provider_accepted`로 기록한다. 이는 실제 받은편지함 도착과 다르다.
- 제공자 호출 **전**의 확정된 일시 실패만 제한적으로 재시도한다. 호출 중 타임아웃·네트워크 단절·5xx처럼 수락 여부를 알 수 없는 결과는 `delivery_uncertain`으로 닫아 자동 중복 발송을 피한다. 운영자 화면에서 접수번호와 상태를 확인하고 필요한 경우 수동 처리할 수 있다.
- 문의 원본과 메일 연결 상태는 고객 테넌트 데이터와 분리한다. 운영자 전용 조회에는 필요한 회신 정보만 표시하고, 조회·연결 동작은 기존 운영자 인증을 요구한다.

## 품질과 검증

- API: 유효성, 멱등성, 속도 제한, 동의, 권한, 전송 결과 분류, 90일 삭제, 메일 본문 이스케이프를 테스트한다. 제공자 호출은 테스트 대역으로 검증하고 실제 메일은 자동 테스트에서 보내지 않는다.
- Web: 공개 경로가 인증 API를 호출하지 않는지, 로그인/기존 경로가 유지되는지, 양식 제출·응답 유실·오류·키보드 동작을 테스트한다. 1440/1024/390/320px의 가로 넘침과 축소 동작을 브라우저에서 확인한다.
- 빌드·타입검사·관련 테스트를 완료하고, 메뉴 문서 `docs/menus/landing.md`, 운영자 메뉴 문서와 `docs/database-schema.md`, `docs/project-status.md`를 같은 작업에서 갱신한다. 운영 자격 증명 입력과 실제 NAVER WORKS OAuth 연결·발송은 배포 환경에서 별도 설정 및 확인이 필요하다.
