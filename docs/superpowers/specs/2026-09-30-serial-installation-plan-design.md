# 제조 일련번호 기반 최초 설치 최종 설계

기준일: 2026-09-30

## 목적과 확정 범위

제조 단계에서 모든 조명 제품에 고유 일련번호를 부여하고, 설치 전에 각 제품의 현장·층·위치를 확정한다. 현장 관리자는 준비된 목록을 한 번 가져와 맵의 예정 위치를 일괄 표시하고, 장비가 검색되면 일련번호에 연결된 실제 장비 신원으로 해당 위치에 일괄 등록한다. 제품마다 현장에서 QR을 찍거나 맵에 한 개씩 끌어 놓는 절차는 필수로 두지 않는다.

사용자가 확정한 조건은 다음과 같다.

- 일련번호는 제조 단계에서 제품마다 붙이고 제조 정보는 현장 설치 전에 중앙 DB에 등록한다.
- 위치는 설치 전에 모두 결정하며, **도면과 별도의 설치 목록**에 좌표와 일련번호를 함께 보관한다.
- 도면마다 CAD 블록·심볼 모양이 다르고 구형 건물은 심볼이 없을 수 있다. 심볼 인식에 설치 성공을 의존하지 않는다.
- 기존 Gateway claim, 개별·일괄 조명 등록, CAD/이미지 맵 편집, 수동 배치·식별·제어 흐름은 유지한다.

이 설계는 조명 제품의 제조 신원, 설치 예정 위치, 실제 통신 등록, 사람이 확인한 물리 위치를 **서로 다른 사실**로 취급한다. 등록 가능한 통신 장비가 없는 제품도 제조 원장에는 일련번호를 가질 수 있지만 자동 통신 등록 대상은 아니다.

## 결정: 앱 논리 맵 좌표를 정본으로 사용

설치 목록의 `x`, `y`는 브라우저 화면 픽셀도, 원본 CAD의 임의 UCS/OCS 좌표도 아닌 현재 층 맵의 논리 좌표다. 현재 공통 맵의 활성 `FloorMapGeneration.width/height`(구형 화면은 `FloorPlan.width/height`) 안에서 `Fixture.x/y`, `FloorLightSlot.x/y`와 같은 좌표계로 저장한다. 원점·축 방향·단위는 선택한 층 맵 설명과 다운로드 양식에 명시하고, 확대·스크롤·화면 크기와 무관하게 저장한다.

| 대안 | 장점 | 이 작업에서의 한계 |
| --- | --- | --- |
| CAD 원본 좌표를 정본으로 사용 | CAD 점 목록을 그대로 가져오기 쉽다 | 도면별 좌표계·원점·축·단위와 이미지 도면의 좌표 부재가 모든 후속 기능으로 전파된다 |
| **앱 논리 맵 좌표를 정본으로 사용** | 현재 맵·Fixture 계약과 일치하고 CAD 심볼 없는 도면에도 동일하게 적용된다 | CAD 점 목록은 가져오기 전에 현재 맵 변환을 한 번 확인해야 한다 |
| 화면 픽셀을 정본으로 사용 | 화면에서 읽기 쉽다 | 줌·화면 크기에 따라 값이 달라져 영속 위치로 사용할 수 없다 |

CAD 원본 좌표 목록이 있다면 현재 `FloorCadScene`의 확정된 원본→논리 맵 변환으로 변환하고, 미리보기에서 원점·축·방향·샘플 위치를 확인한 뒤 **논리 좌표만** 설치 계획에 저장한다. 변환 메타데이터가 없거나 일치하지 않으면 임의 추정하지 않고 가져오기를 중단한다. 이미지·구형 도면은 등록된 이미지 맵의 논리 좌표를 사용한다. 심볼이 전혀 없어도 위치 목록 자체가 입력이다. 선택한 지점을 논리 좌표로 내려받는 양식은 보조 도구이며, 목록의 정본이나 필수 단계는 아니다.

## 데이터와 소유권

### 1. 제조 원장 `LuminaireInventory`

중앙 DB에 `manufacturerSerial`(정규화 후 전역 유일), 제품 모델·정격전력·제조 상태, 자동 등록 가능한 모델의 실제 `deviceUuid`(전역 유일, 없을 수 있음)를 보관한다. 제조 스테이션이 제품에 인쇄한 일련번호와 실제 장비의 Device UUID를 출고 전에 같은 원장에 기록한다. 일련번호는 공개 식별자이지 비밀번호나 인증 수단이 아니다. 제조 원장의 serial↔UUID 연결은 현장 관리자에게 임의 수정 권한을 주지 않고, 제조 스테이션 인증 경계에서만 생성·정정한다. 정정은 이력과 충돌 검사를 남긴다.

현재 Gateway 검색 응답의 `serialNumber`는 실제 제품 일련번호가 아니라 `deviceUuid`를 복사한 값이므로 제조 원장의 근거로 사용하지 않는다. 초기 버전은 펌웨어 UUID 형식을 변경하지 않고 제조 단계에서 **현재 실제 UUID를 읽어 매핑**한다. 기존 제조 매핑이 없는 설치 제품은 현재의 수동 등록 경로로 남기며, 새 일괄 자동 연결에 끼워 넣지 않는다.

### 2. 설치 계획 `InstallationPlan` / `InstallationPlanItem`

계획은 층별 버전과 상태(`active`, `superseded`, `stale`)를 가진다. 미리보기는 저장하지 않는다. 한 층에는 활성 계획이 하나만 있으며 한 번의 현장 파일 업로드가 여러 층 계획을 하나의 가져오기 작업으로 원자적으로 확정할 수 있다. 각 계획은 현장·층, 가져오기 파일의 해시, 작성자, 확정 시각, 활성화 당시 맵 좌표 프레임 버전과 `Floor.mapRevision`을 기록한다. 좌표 프레임 버전은 새 `Floor.coordinateFrameVersion`으로 관리하고 맵 교체·크기/원점/축/변환 변경에만 올린다. 장식 편집에 따른 일반 revision 상승만으로 계획을 무효화하지 않는다. 항목은 `positionCode`(층 안에서 고정된 위치 ID), `manufacturerSerial`, 논리 `x/y`, 선택적인 CAD 슬롯 연결, 실제 등록 후의 `fixtureId`를 가진다.

활성 계획에서 `(floorId, positionCode)`와 `manufacturerSerial`은 각각 중복될 수 없다. 같은 제조 일련번호를 서로 다른 현장·층에 동시에 예약하지 않는다. 좌표 변경은 위치 ID를 재사용한 새 계획 버전으로 기록하며 과거 계획을 조용히 덮어쓰지 않는다. 기존 실제 Fixture를 다른 위치에 자동 이동하거나 삭제하지 않는다. CAD 전용 `FloorLightSlot`은 승인된 CAD 후보를 요구하고 CAD 재적용 시 교체되므로, 심볼 없는 예정 위치를 이 테이블에 가짜 후보로 생성하지 않는다. CAD 슬롯 연결은 있을 때만 선택적으로 사용한다.

입력 파일의 첫 버전은 UTF-8 CSV다. 현장은 화면에서 선택하고 행은 아래 다섯 열을 가진다. `floorCode`는 파일 안에서 사용하는 층 구분값이다. 미리보기에서 코드별로 실제 `Floor.id`를 한 번 매핑하고 확정 시 그 ID를 저장한다. 층 이름이나 `level`이 중복돼도 추측해서 다른 층에 배치하지 않으며 새 Floor 필드를 요구하지 않는다. 파일의 숫자는 현재 맵 논리 좌표이며 소수도 허용한다.

```csv
floorCode,positionCode,x,y,manufacturerSerial
B2,B2-A-001,1840.5,920.0,LED-2026-000001
B2,B2-A-002,1910.0,920.0,LED-2026-000002
```

제품 모델·정격전력·Device UUID는 제조 원장에서 조회하고 현장 CSV에 중복 기입하지 않는다. 한 층의 계획 항목은 첫 버전에서 최대 2,000개로 제한하고 초과 파일은 명시적으로 거부한다. 파일 행 번호별 오류를 보여주며 일부 행만 몰래 적용하지 않는다.

### 3. 실제 등록 데이터

`MeshNode`와 `Fixture`는 장비 등록 성공 후 기존 흐름으로 생성한다. 계획 항목은 실제 Fixture가 아니다. 미검색·등록 실패 제품에 가짜 Fixture, online 상태, 제어 대상이나 에너지 사용량을 만들지 않는다. 등록 성공 후에는 같은 DB 거래에서 계획 항목을 생성된 Fixture에 연결하고 `Fixture`를 계획 좌표에 `placed`로 배치하되 `positionVerifiedAt`은 `NULL`로 둔다. 이는 **계획 위치에 배치된 표시**이지 실제 제품이 그 자리에서 확인되었다는 뜻이 아니다. 사람이 해당 위치를 확인했을 때만 기존 위치 검증 시각을 기록한다.

CAD 슬롯이 유일하고 현재 맵에서 유효하면 기존 1:1·동일 층·정확한 좌표 제약을 지키며 할당한다. 슬롯이 없거나 매칭이 애매해도 좌표 배치는 가능하지만 자동으로 임의 슬롯을 선택하지 않는다.

## 사용자 흐름과 API 경계

1. 제조 스테이션이 제품별 일련번호, 모델, 실제 Device UUID를 중앙 원장에 일괄 등록한다. 중복·형식 오류·이미 다른 제품에 연결된 UUID는 거부한다. 제조 원장이 없으면 현장 파일 업로드 전에 해당 행을 오류로 보여준다.
2. 관리자가 설정의 설치 계획 화면에서 현장과 맵을 확인하고 CSV를 올린다. API의 **미리보기**는 읽기 전용으로 모든 행을 검증하고 층 맵 위에 예정 위치를 겹쳐 보여준다. 제조 원장 누락, 중복, 다른 현장 예약, 이미 등록된 제품과의 충돌, 층 부재, 좌표 범위 밖, 유효하지 않은 수치, 맵 프레임 변경을 행별로 보고한다.
3. 관리자가 미리보기를 승인하면 API가 파일 해시·대상 현장·맵 revision을 다시 확인하고 층별 활성 계획을 하나의 DB 거래에서 확정한다. 같은 요청 재전송은 같은 결과를 반환하며, 내용 또는 맵이 달라진 요청은 새 확인을 요구한다. 이 시점에 모니터링 맵은 **설치 예정** 마커를 읽기 전용으로 보여주되 실제 조명 수·상태 KPI와 합치지 않는다.
4. 관리자가 연결된 Gateway를 선택해 **일괄 등록 시작**을 한 번 누른다. API는 활성 계획에 있는 제품만 허용 목록으로 삼아 기존 층별 등록 세션·검색·배치 등록·MQTT outbox를 순차적으로 사용한다. 한 Gateway가 여러 층을 담당해도 단순 RSSI로 층을 추정하지 않고 제조 UUID→일련번호→계획 층으로만 분류한다. 원장 UUID가 없거나 예상 층·현장·Gateway scope와 충돌하면 자동 등록하지 않는다. 관리자는 진행률과 예외를 보고 다시 이어갈 수 있다.
5. Gateway의 실제 provisioning terminal 성공을 받은 뒤에만 `MeshNode`/`Fixture`와 계획 항목을 원자적으로 연결한다. 기존 상태 수집 규칙에 따라 online/offline을 판정하며, 등록 성공을 통신 가능·물리 설치 검증 완료로 과장하지 않는다. 현장 확인 후 검증 상태를 별도 갱신한다.

외부 계약은 제조 원장 쓰기(제조 스테이션 인증), 계획 미리보기·확정·조회(현장 관리자, 조회는 권한 있는 viewer), 일괄 시작·진행/재개·항목 예외 확인(현장 관리자)으로 나눈다. 기존 `/registration-sessions`의 의미를 몰래 바꾸지 않고 기존 서비스의 안전한 등록 경로를 재사용하는 조정 계층을 둔다. 미리보기는 DB·Gateway를 변경하지 않는다. 계획 확정은 DB 거래지만 RF 검색/등록은 비동기 작업이며 전체 현장 장비를 하나의 거래로 성공 처리하지 않는다.

## 실패·수정·맵 변경 규칙

- 미검색 장비는 `설치 예정/미검색`, RF 등록 중은 `진행 중`, terminal 성공은 `등록됨/위치 미확인`, 사람 확인 뒤 `위치 확인`으로 표시한다. 실패 원인은 기존 등록 세션의 상태에서 읽고 다시 시도 가능한 행과 `reconcile_required` 행을 구분한다. 후자는 자동 재시도하지 않는다.
- 중복 UUID/일련번호, 다른 현장 소유 장비, plan과 검색 결과 불일치, 다른 층에 이미 연결된 Fixture는 실패 닫힘 처리한다. 동일 파일 재전송·늦은 ACK·프로세스 재시작은 동일 결과 또는 안전한 중단이어야 한다.
- 조명 교체는 기존 계획 항목의 serial을 덮어쓰지 않는다. 관리자 명시적인 교체 흐름에서 이전 제품의 링크·이력을 보존하고 새 제조 serial을 확인한 뒤 새 계획 버전과 등록을 연결한다. 이미 제어·통계에 사용된 Fixture의 신원 재사용은 금지한다.
- 맵 편집과 계획 확정은 같은 층 revision을 잠가 경쟁을 검사한다. CAD 재적용, 맵 크기·원점·변환 변경으로 좌표 프레임이 바뀌면 활성 계획을 `stale`로 표시하고 후속 자동 배치·등록을 중단한다. 기존 CAD 적용의 Fixture 미배치 전환은 유지하고, 관리자가 새 맵에서 다시 미리보고 계획을 재확정해야 한다. 단순 장식 편집은 좌표 프레임이 동일하면 계획을 유지한다.
- UI에서 계획 마커와 실제 Fixture 마커는 형태·범례·설명으로 구분한다. `등록됨/위치 미확인`도 완료로 오인하지 않게 표시한다. viewer에게 가져오기·등록·교체 쓰기 권한을 주지 않는다.

## 기존 기능과 문서에 미치는 영향

- 설정: 현장 관리자용 계획 가져오기·미리보기·확정·일괄 등록 진행/예외 화면을 기존 조명 등록 주변에 추가한다. 기존 수동 등록은 그대로 남긴다.
- 모니터링: 계획/실제/확인 완료를 별도 범례와 집계로 보여준다. 기존 실제 장비 KPI, 로그, 지도 조작과 제어 진입은 유지한다.
- 제어·통계: 계획만 존재하는 제품은 명령·에너지·비용·상태 집계에서 제외한다. 실제 Fixture가 생긴 뒤부터 기존 기능에 편입한다.
- DB/API 구현 시에는 Prisma migration과 `docs/database-schema.md`를 같은 작업에서 갱신하고, 설정·모니터링 및 실제로 변경되는 다른 메뉴의 `docs/menus/*.md`도 기능 코드와 함께 갱신한다.

## 검증·수용 기준

- 제조 CSV에 500개 제품을 미리 넣고, 두 층의 위치+serial CSV 한 번으로 정확히 500개 **예정 마커**가 표시된다. 이 단계에서 Fixture/에너지/제어 대상 수는 변하지 않는다.
- 서로 다른 CAD 심볼 이름·회전이 섞인 도면과 조명 심볼이 전혀 없는 이미지 도면에서 동일한 설치 계획 형식이 동작한다. CAD 좌표 입력을 변환할 때 원점·축 검토에 실패하면 적용하지 않는다.
- 검색된 UUID가 제조 원장의 일련번호 하나와 계획 위치 하나에만 연결된다. 등록 terminal 성공 행만 실제 Fixture를 생성·배치하고, 미검색·실패 행은 예정 상태로 남는다. 위치 확인 시각은 사람이 확인하기 전까지 비어 있다.
- 중복 serial/UUID, 두 현장 경쟁, 좌표 범위 밖, stale 맵, 이미 등록된 제품, 다른 층 충돌, 늦은 terminal, 재시작·중복 요청과 `reconcile_required`를 자동·실제 PostgreSQL 통합 테스트에서 검증한다.
- 기존 개별·배치 등록, Gateway claim, 수동 맵 배치, CAD 재적용, 모니터링, 제어·통계 회귀가 통과한다. Raspberry Pi/BlueZ/ESP32-H2와 실제 조명의 현장 HIL은 별도 승인 관문으로 남기고 자동 테스트 통과를 양산 검증으로 표현하지 않는다.

## 이번 설계에서 제외

일련번호를 이용한 새 펌웨어 UUID 생성, 제품별 설치 시 QR 스캔 강제, CAD 심볼 자동 인식의 완벽한 분류, RF 신호 세기로 층·물리 위치를 판정하는 기능, 무선 성공만으로 설치 확인을 자동 완료하는 기능은 포함하지 않는다. 이번 문서는 구현 승인이나 중앙 DB 변경 실행 지시가 아니며, 구현 계획과 실제 DB migration·현장 적용은 다음 단계에서 별도로 검토한다.

## 판단 근거

- Bluetooth SIG의 [Mesh Remote Provisioning 설명](https://www.bluetooth.com/mesh-remote-provisioning/)은 검색되는 장비의 Device UUID가 제조 시 부여되는 장비 식별자이며 검색 보고에도 포함된다고 설명한다. 따라서 제조 일련번호와 UUID를 출고 전 묶어 두는 방향을 택했다. UUID 자체를 제품 일련번호나 인증 비밀값으로 혼동하지 않는다.
- Autodesk의 [DXF 객체 좌표계 설명](https://help.autodesk.com/cloudhelp/2024/ENU/AutoCAD-DXF/files/GUID-D99F1509-E4E4-47A3-8691-92EA07DC88F5.htm)은 원본 DXF 요소가 객체 좌표계를 쓸 수 있음을 설명한다. 서로 다른 원본 좌표를 그대로 제품 위치 정본으로 삼지 않는 이유다.
