# BIO 센서 조명의 공통 등록·UI 설정 설계

기준일: 2026-10-08

상태: 2026-10-08 사용자가 문서 제시 후 `구현 계획 작성 후 바로 진행해줘`로 코드 구현 진행을 승인했다. 실제 운영 적용 승인은 별도다.

## 목적과 범위

사용자는 특정 A/B에 고정된 연결이 아니라, 조명이 늘어나도 개발자가 개별 연결 코드나 배포 설정을 추가하지 않고 서비스 UI에서 센서 제어를 설정하길 원한다. 등록된 BIO 조명 전체에 공통 준비 확인 흐름을 제공하고, 호환성이 확인된 센서 조명과 같은 게이트웨이의 제어 조명을 이벤트 화면에서 선택한다.

‘전체 조명에 공통 UI 제공’과 ‘모든 하드웨어의 센서 지원 보장’을 구분한다. 센서가 없거나 식별·프로토콜 근거가 부족한 장비는 사유와 다음 조치를 표시한다. 미검증 장비를 사용 가능으로 위조하지 않는다. BlueZ 제거는 이번 구현에 포함하지 않고, BIO 경로는 BlueZ 없이 동작해야 한다.

이 설계는 [기존 펄스 이벤트 설계](2026-09-30-bio-sensor-pulse-event-control-design.md)의 공통 프로파일 공급·장비 준비 확인·UI 연결을 보완한다. 기존 펄스 수명주기, source 보호, 수동 우선순위, 원복·장애 정책은 유지한다. A/B는 설명용 역할 이름일 뿐, ID·주소·장비 수를 코드에 고정하지 않는다.

## 선택한 접근

장비군의 호환 정보와 개별 장비의 현재 준비 상태를 분리한다.

- **공통 호환 프로파일:** 검증된 장비 식별 조합, 허용된 exact 알림 body, 독립 링크 확인 방법과 신선도 조건을 버전형 데이터로 관리한다. 같은 검증 조합의 새 조명은 이 데이터를 재사용한다.
- **장비별 자동 준비 확인:** confirmed 등록, 현재 site/gateway/assignment, 실제 장비 식별, 센서 모드와 독립 링크 상태를 공통 작업이 확인한다. 조명마다 필요한 실제 신원 확인은 자동화하고 개발자 작업을 요구하지 않는다.
- **일반 사용자 UI:** 센서 선택 → 실행 조명 선택 → 밝기·유지시간 → 저장으로 끝난다. raw packet, fingerprint, native 주소와 자격 증명은 일반 UI에 노출하지 않는다.

조명별 하드코딩은 확장 요구를 충족하지 못하므로 제외한다. 후보 알림이나 모드 GET만으로 전체 조명을 지원 처리하는 방식도 제외한다. 모든 조명에 장시간 현장 시험을 일괄 강제하지 않으며, 새로운 장비군의 호환 검증과 기존 장비군 조명 추가를 구분한다.

## 실제 식별과 프로파일 재사용

현재 durable mapping의 `firmware` 버전 문자열과 `protocol=crc16`만으로 센서 종류나 제조사 모델을 판정하지 않는다. 현재 decoder의 discovery가 보존하는 `deviceType`, `firmware.major/minor/revision/build`, `sensorType`, `infraredType`, `ambientLightType`, `hardwareType` 전체를 정규화된 관측 fingerprint로 사용한다. 이것은 관측 식별 조합이지 제조사 모델명이나 감지 회로 건강 인증이 아니다.

펌웨어 담당 검토에서 이 조합은 매칭 키로 사용할 수 있으나 동일 하드웨어 변형·감지 동작을 보장하는 충분조건이 아님을 확인했다. 프로파일 승인 근거에 식별 조합의 실제 재사용 범위를 명시한다. 현재 `bio-dongle-client.ts`의 `toDiscoveredDevice`가 종류 필드를 버리므로 decoder만 수정하는 것으로 끝내지 않고 discovery→등록/저장→준비 작업 경계 전체에서 해당 관측을 보존·전달한다.

프로파일은 ID·revision·관측 fingerprint·허용 exact body 목록·독립 링크 확인 정책·검증 근거 digest·승인/철회 상태를 가진다. 검증된 프로파일은 native UUID나 특정 A/B ID로 제한하지 않지만, 실제 실행권한은 개별 장비의 현재 binding에 묶는다. 식별 정보가 없거나 둘 이상의 프로파일과 모호하게 매칭되면 사용을 막는다. `sensorType` 숫자의 센서 유무 의미도 승인된 프로파일의 판정 근거 없이 추측하지 않는다.

프로파일 카탈로그는 서비스 관리 권한으로 관리되는 버전형 데이터다. Gateway에 현재 인증 scope로 전달하고 내구 저장·수용 확인하며, 로컬 임의 env나 UI 입력으로 승격하지 않는다. 신규 동일 조합은 코드 수정·이미지 재배포 없이 자동 매칭한다. 새로운 통신 방식이나 decoder 자체가 다른 장비군은 별도 호환 구현이 필요할 수 있으며 데이터 등록만으로 해결됐다고 표시하지 않는다.

현재 source는 생성 시 프로파일 목록을 고정한다. 동적 카탈로그는 새 revision을 검증한 뒤 프로파일과 authority를 같은 수명 경계에서 교체하고, 이전 권한·대기 알림을 철회한다. 변경된 프로파일로 이전 알림을 재소비하거나 오래된 `ready`를 유지하지 않는다. 기존 활성 대상·미확정 원장을 삭제하지 않고 장애/명시 해제 경로로 넘긴다.

현재 승인 프로파일 목록은 비어 있다. 10월8일 pilot의 `0101000000000000` 알림 5건과 B 적용/연장/복귀 증거를 참고하되, 이를 전체 firmware qualification 또는 미검증 `05` body 허용으로 전환하지 않는다. 실제 초기 지원 프로파일의 승인 근거 확보는 제품 활성화와 별도 완료 항목으로 기록한다.

## 등록·설정 흐름

1. 등록 완료 후 현재 discovery 식별을 보존하고 카탈로그와 자동 대조한다. 기존 조명도 같은 공통 ‘준비 상태 확인’ 작업으로 갱신한다. 기존 ID·밝기·전원·그룹·등록 이력은 보존한다.
2. 등록 자체는 읽기·분류만 수행하며, 조명을 자동으로 센서 모드로 바꾸지 않는다. 사용자가 UI의 ‘센서 사용 설정’을 누르면 기존 `ensure_sensor` 작업과 별도 GET 확인을 재사용한다. 상태 확인은 `query`로 수행하고 SET을 보내지 않는다.
3. 작업은 비동기 진행·결과·재조회·부분 실패를 장비별로 표시한다. 반복 클릭은 같은 요청의 중복 쓰기를 만들지 않는다. 재시작·재배정·주소/식별 변경·프로파일 철회 시 기존 준비 증거를 무효화한다.
4. 모드 확인과 실제 센서 호환성을 분리한다. `modeVerified=true`만으로 `ready`를 생성하지 않는다. 준비된 동일 조합의 장비는 사용자에게 별도 랩 연결·브라우저 시험·개발자 승인 파일을 요구하지 않는다.

모드 GET에는 요청 transaction ID가 없으므로 여러 조명의 준비 확인도 기존 단일 client의 전역 직렬 큐를 공유한다. 요청 취소/timeout 후 늦은 응답을 다음 장비·작업의 성공으로 사용하지 않으며 기존 연결 generation 폐기·UUID/주소/network/mapping 검증을 유지한다. UI 진행 표시는 장비별로 하되 RF GET를 조명별 병렬 client로 확장하지 않는다.

## 제어 UI

- 기존 지도 기반 선택기를 유지한다. 모든 등록 조명에 상태와 사용 불가 이유를 제공하고, 센서로 사용 가능한 조명만 source로 확정할 수 있다. 미준비 장비도 숨기지 않고 ‘센서 사용 설정’ 또는 ‘준비 상태 확인’으로 이동할 수 있게 한다.
- A/B 전용 제품 문구는 ‘감지 센서’와 ‘실행 조명’으로 교체한다. 최초 BIO 규칙은 센서 1개와 하나 이상의 실행 조명을 사용하되 어떤 특정 조명 ID도 고정하지 않는다. 여러 규칙에 서로 다른 센서를 설정할 수 있다. 한 규칙의 복수 BIO 센서 합성은 별도 확장이다.
- 밝기와 유지시간은 기존 입력을 재사용한다. BIO 유지시간 10~1,800초, 기본60초를 유지하고 저장 후 수정 가능하게 한다. 10초의 알림 공백 중 복귀/재점등 가능성을 안내한다.
- 같은 site/gateway의 실행 조명만 허용하고 센서 source 자신 및 다른 활성 BIO source는 실행 대상에서 제외한다. 센서 조명 자체의 자율 점등은 유지하지만 source의 밝기까지 서비스에서 쓰는 기능은 이번 범위가 아니다.
- ‘사용 가능’, ‘설정 필요’, ‘호환 확인 필요’, ‘연결 이상’, ‘지원하지 않음’을 사용자 문구로 구분한다. 내부 상태는 모드·프로파일·binding·링크의 사유를 각각 보존한다. 마지막 알림·장애·복원 대기는 확인된 실제 데이터만 표시한다.
- 기존 공통 Button/Card/Text/지도 컴포넌트를 재사용하고 센서 상태·준비 작업 컴포넌트도 공통화한다. PC 페이지 전체 스크롤/잘림을 만들지 않으며 모바일 지도 pinch와 터치 조작을 유지한다.

## 서버·Gateway 연결과 장애

서버가 프로파일과 사용자 권한을 관리하고, Gateway가 단일 USB client에서 현재 discovery·binding·독립 링크 확인으로 실제 authority를 생산한다. 기존 source intake → product controller → hold/target 원복 경로와 capability의 인증 전달/정확 ACK를 재사용한다. ACK는 전달 확인이고 qualification 또는 현재 링크 건강이 아니다.

센서 준비 작업은 raw 장비 정보 대신 typed fingerprint·프로파일 ID/revision·작업 상태·차단 사유를 공유 계약으로 전달한다. 기존 strict V1/V2 payload에 필드를 조용히 추가하지 않고 새 버전 계약을 정의한 뒤 서버→Gateway→Web 소비 순서로 적용한다. 현재 canonical MeshNode와 Fixture의 독립 식별·assignment 검증을 유지한다.

독립 GET는 링크 응답만 확인하며 감지 회로 건강으로 표현하지 않는다. 링크 확인의 주기·기한은 검증된 프로파일 정책이 소유하고, 수신 pulse 자체로 건강을 생성하지 않는다. 연결 이상에서 새 활성화와 건강한 만료를 멈추고 대상 원상태/미확정 원장을 보존한다. 기존 명시적 운영자 해제와 회복 후 full-hold 관찰을 재사용한다. 기존 현장 장애 담당자·조치 정책이 없는 현장의 상시 활성화는 준비 UI와 별도로 막는다.

## 구현·검증 경계와 완료 기준

재사용 경계는 `apps/gateway/src/bio/{bio-command-codec,bio-sensor-pulse-source,bio-capability-delivery}.ts`, `apps/gateway/src/adapters/adapter-factory.ts`, Gateway 센서 모드 handler, `apps/api/src/commands/sensor-mode-operations.service.ts`, API capability/등록/dashboard, `apps/web/src/features/control/automation/{VehicleEventDialog,VehicleEventSourceStatus}.tsx`다. 새로운 책임은 공통 프로파일 카탈로그, 관측 fingerprint, 장비 준비 작업·authority 공급이다. 세부 파일·필드·migration은 문서 승인 후 실행 계획에서 확정한다.

최소 검증은 가짜 장비의 서로 다른 ID 3개를 사용해 같은 프로파일 재사용·잘못된 조합 거절·확인 작업·UI 규칙 저장→인증 전달→hold/원복까지 연결한다. 모드만 성공/프로파일 미확정/링크 불명확/재배정/철회·늦은 응답·부분 실패도 집중 검증한다. 기존 전체 회귀나 장시간 현장 시험을 무조건 반복하지 않는다. 자동 테스트 통과와 실제 호환 지원을 분리한다.

완료 시 조명 추가를 위해 특정 ID 코드 수정·새 이미지 배포·개발자 연결 설정이 필요하지 않아야 한다. 실제 지원 가능 판정은 승인 프로파일과 현재 장비 준비 증거가 있는 조명에만 허용한다. API/DB schema 변경 시 `docs/database-schema.md`, UI/흐름 변경 시 제어·설정·모니터링 메뉴 문서와 상태판/체크리스트를 갱신한다.

실제 DB migration, Gateway 배포/재시작, 센서 모드 변경과 초기 프로파일 지원 전환은 코드 작업과 분리하여 사용자에게 범위를 알리고 승인 후 수행한다. 이 설계 문서 작성은 해당 운영 변경이나 새 현장 시험을 실행하지 않는다.
