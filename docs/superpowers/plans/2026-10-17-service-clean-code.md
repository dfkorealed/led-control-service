# 서비스 전체 클린 코드 정리 실행 계획

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 서비스 전체의 클린 코드 정책과 자동 검사를 정착시키고, 파일별 전수 검토 및 동작 보존 정리를 증거와 함께 완료한다.

**Architecture:** 독립적으로 검증 가능한 정책·검사 기반, 확정된 소규모 정리, 전수 검토·고위험 경계·최종 검증의 세 하위 계획으로 나눈다. 처음부터 큰 서비스 전체를 재작성하지 않는다. 하나의 파일별 점검 원장과 구체적인 진단 원장을 사용하고 변경·검증·검토를 작은 단위로 통합한다.

**Tech Stack:** Node22, pnpm9.15.0, 기존 TypeScript/React/NestJS/Prisma/Vitest/Jest/Playwright, C·shell, ESLint/typescript-eslint·Prettier.

**Spec:** [승인된 설계](../specs/2026-10-17-service-clean-code-design.md).

상태: **서면 설계 승인 완료, 실행 계획·실행 방식 검토 대기**. 계획 작성 기준은 `2f1cd047f1d9fa23f2634a6286d783ffc66371a5`다. 구현 기준 소스는 실행 시작 시 다시 고정하며 다른 작업을 과거 커밋으로 되돌리지 않는다.

## Global Constraints

- Node22·pnpm9.15.0을 사용한다. Web과 Mobile의 서로 다른 React·TypeScript 버전을 정리 명목으로 통일하지 않는다.
- TS/JS 포맷은 2칸, 세미콜론, 큰따옴표, 후행 쉼표 없음, LF, 목표 100자다. 길이는 책임 검토 신호이지 강제 분할 기준이 아니다.
- API/DB/MQTT/BIO wire·hash·오류 의미·timeout/retry·주소·기본 밝기·권한·상태 전이·영속 저장 버전은 유지한다.
- schema/migration·기존 ID·legacy/native·키/인증서·실제 env·실행 서버·장비·클라우드 자원은 변경하지 않는다. 실장비 검증·배포·운영 반영은 별도 승인이다.
- 공통 UI·디자인 토큰과 UI 정책을 유지하고 디자인 시스템 병행 작업을 섞지 않는다. 변경 메뉴의 기능 현황·관련 파일을 같은 변경 단위에서 갱신한다.
- 포맷과 구조 변경은 분리한다. 저장소 전체 자동 수정, 넓은 ignore, 자동 baseline 갱신, 테스트 삭제·시간 제한 완화로 통과시키지 않는다.
- root gate의 준비→consumer·owner lock·signal/drain 순서를 유지한다. 같은 checkout의 root 검증과 fixed-port Lab은 병렬 실행하지 않는다.
- 기존 실패·skip·미검증은 현재 성공으로 간주하지 않는다. 기존 실패가 있으면 같은 소스/환경의 원본 증거와 새 회귀를 구분한다.
- 사용자의 AGENTS/상태판 미커밋 변경 및 다른 작업 자원을 보존한다. 다른 채팅에 메시지를 보내지 않는다.

## Review Focus

1. 새 파일·이름 변경·symlink·비밀 파일이 inventory를 우회하거나 원장 변경 자체가 검토 완료로 오인됨 → F1의 누락/경로/해시/완료 판정 회귀.
2. 기존 위반을 복제하거나 baseline을 갱신해 새 실패가 숨겨짐 → F3의 다중 집합 비교·stale 예외·normal check 무쓰기 회귀.
3. 타입 개선이 UUID spelling·날짜 정밀도·coercion·null/빈값 의미를 변경함 → R2/R3/R4의 실제 경계 회귀.
4. timeout·지연 응답·오래된 operation이 취소/성공/잠금 해제로 잘못 바뀜 → R1/R6/R7 및 Q2의 경계 회귀.
5. 큰 파일 이동이 commit/ACK·소유 세대·복구·fsync·종료 순서를 변경함 → Q2의 호출/상태 전이 표와 실제 covering 관문.

## 실행 순서와 소유권

1. F1→F2→F3 순서로 기반을 검증한다. root 설정/lockfile/CI writer는 한 명이다.
2. R1/R2/R4/R5 등 소유 파일이 다른 작업만 독립 구현할 수 있다. 같은 checkout의 준비·빌드·root gate는 직렬화한다.
3. R3 shared 이동은 지정 한 소유자만 수행하고 검증된 커밋 뒤 API/Web/Mobile/Gateway 소비 검증을 순차 수행한다. R6/R7/R8과 Web 디자인 작업은 파일 소유권을 확인한다.
4. Q1은 전수 점검을 실제로 수행한다. R 작업으로 이미 확인한 파일도 최종 내용 해시가 일치하는 경우만 재사용한다. Q2는 고위험 분해가 필요한 파일의 covering과 구체 경계를 먼저 확정한다.
5. Q3에서 최종 원장·예외·소스·전체 검증을 대조한다. 로컬 병합이나 실행 서비스 갱신은 자동 수행하지 않는다.

대량 영역 작업은 총괄이 담당 역할 서브에이전트에 나누고 결과와 이 체크리스트를 통합한다. 작은 수정은 사용자의 직접 처리 기준을 따른다. 실행 방식의 최종 선택은 계획 검토 뒤 사용자에게 받는다. 권장은 역할별 구현 및 작업별 독립 검토이며, Native 선택 시에도 마지막 독립 검토는 유지한다.

## 공통 작업 종료 절차

각 F/R 작업과 Q1의 각 영역 묶음은 다음 절차로 닫는다. 하위 계획에서 이 절차를 참조하면 이 다섯 항목을 모두 수행한다.

- [ ] 지정 회귀의 RED 또는 기존 동작 covering을 먼저 확인한다. 단순 이동은 존재하는 테스트를 활용하되 새 직접 소비 경계는 검증한다.
- [ ] 최소 수정 후 같은 covering을 GREEN으로 확인하고 직접 관련 타입·정적 검사·포맷을 실행한다. 임의 파일 전체 자동 수정은 금지한다.
- [ ] 공개 경로·오류·입출력·순서와 diff를 검토하고 새 회귀를 해결한다. 기준선의 실패는 별도 보존한다.
- [ ] 해당 파일 원장·예외·영향 메뉴의 관련 경로·상태판 및 현재 작업 체크리스트를 함께 갱신한다.
- [ ] `git diff --check`와 정확한 staged 경로를 확인해 해당 작업만 커밋한다. 전체 `git add .`로 사용자 변경을 포함하지 않는다. 독립 검토 지적을 해결한 뒤 다음 의존 작업으로 넘긴다.

## 전체 체크리스트와 완료 판정

설계 대응: CC-01/02/03은 R1/R2/R4/R7과 Q1/Q2, CC-04는 F2와 R2/R3/R5/R8/Q2, CC-05는 R1/R6/R7/Q2, CC-06은 Q1의 Web 묶음과 Q3 UI, CC-07/08은 F1 정책과 Q1/Q2의 주석·삭제/호환성 검토, CC-09/10은 F1–F3와 Q1 형식 전환/Q3 완료 검사로 검증한다. 어느 정책도 자동 lint만으로 충족했다고 판정하지 않는다.

- [x] 설계 승인과 영역별 읽기 전용 계획 입력을 통합했다.
- [x] 세 하위 계획의 파일·인터페이스·검증·위험·완료 기준을 작성하고 메인 self-review를 수행했다.
- [ ] 사용자 실행 계획 검토 및 실행 방식 확정.
- [ ] F1–F3 정책·검사 기반 구현/검토.
- [ ] R1–R8 확정 범위 정리/검토. 안전 관문이 충족되지 않은 작업은 미완료로 남긴다.
- [ ] Q1 전수 검토, Q2 필요한 고위험 하위 설계/정리, Q3 결합 검증/최종 검토.

최종 포함 대상의 미검토·누락·stale hash·판정 없는 파일은 0이어야 한다. 예외는 근거와 재검토 조건이 있어야 하며, 발견한 중대한 정책 위반을 `유지`로 숨기지 않는다. 전체 검토 완료, 모든 테스트 통과, 실기기/HIL 완료는 별개의 판정이다. 새 회귀나 중대한 미해결 위험이 남으면 완료/무조건 병합 가능으로 보고하지 않는다.

계획 작성 중에는 제품 설치/prepare/build/test·브라우저·DB·SSH·실장비·운영 작업을 수행하지 않는다. 문서 검증과 승인 상태 기록만 수행한다.
